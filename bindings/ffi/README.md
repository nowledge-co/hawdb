# HawDB C ABI (`hawdb-ffi`)

A small `extern "C"` surface over `HawDBEmbedded` so non-Rust hosts can
embed HawDB: open a database, run one Cypher or SQL statement per call,
close. The crate builds both `cdylib` and `staticlib` and lives outside
the Cargo workspace, like `bindings/python`.

```sh
cargo build --release           # target/release/libhawdb_ffi.{dylib,so,a}
```

`include/hawdb_ffi.h` is generated by cbindgen during the build and is the
normative contract.

From the repository root, Bazel builds the same C ABI through the embedded
engine target and consumes the checked-in header without rewriting sources:

```sh
bazel build //bindings/ffi:hawdb_ffi //bindings/ffi:hawdb_ffi_static
bazel test //bindings/go:hawdb_go_tests
bazel test //bindings/ffi:hawdb_ffi_tests
```

`hawdb_ffi` produces the platform's shared library; `hawdb_ffi_static` produces
the static archive. The header is available as
`//bindings/ffi:include/hawdb_ffi.h`. Regenerate it with Cargo when changing
the ABI. The Go test target runs with cgo disabled and loads the Bazel-built
shared library from its declared runfiles, so no `HAWDB_LIBRARY` setup or
prebuilt Cargo artifact is required.

Development prereleases also ship these libraries prebuilt for macOS, Linux
(glibc) and Windows, with the header, a manifest and checksums (stable releases
do not); see
[Prebuilt C ABI libraries](../../docs/PREBUILT_LIBRARIES.md).
[`examples/embed.c`](examples/embed.c) is a minimal linked host.

## Owned-result boundary conventions

- **Strings are UTF-8 pointer-plus-length pairs**, never NUL-dependent.
  A NULL pointer is meaningful only where the function documents it as
  "absent" (optional JSON arguments); a required string that is NULL is
  an `invalid_argument` error. `len` is authoritative.
- **`HawdbBuffer { char *ptr; uintptr_t len; }`** carries every output.
  The caller allocates the struct, the library fills it, and the caller
  releases exactly the buffers it received with `hawdb_buffer_free`,
  which also zeroes the struct so a second free is a no-op. The library
  never retains a returned buffer.
- **Errors are out parameters, not thread-locals** — hosts may hop OS
  threads between calls. A failed call fills `err_out` with
  `{"kind": "<snake_case kind>", "message": "<text>"}` and leaves the
  database handle usable. `kind` is the engine's own error variant
  (e.g. `capability_unavailable`, `execution`, `admission`, `stopped`);
  `invalid_argument` marks caller-side contract violations,
  `transaction_open` / `no_transaction` transaction-state misuse, and `panic`
  a contained Rust panic.
- **Resource refusals**: memory-ledger and spill-quota failures use
  `kind: "resource_budget_exceeded"` and add a `resource_budget` object with
  `resource`, `scope`, `owner`, `memory_class` (nullable), `requested`, `used`,
  `budget`, and `budget_option`. The message is unchanged. Counts are unsigned
  64-bit integers; hosts must preserve their precision. `requested` is the
  additional charge, or the net increase for a query-level ownership transfer.
  The option names the effective host limit, runtime grant, or constructor
  argument. Filesystem failures report usable space after the configured
  minimum free-space reserve, so raising that minimum reduces usable space.
  Existing descriptor errors and ordinary error JSON remain unchanged. The
  [resource metadata contract](../../docs/EXECUTION_REQUEST_CONTRACT.md#resource-refusal-metadata)
  lists built-in budget origins; hosts must tolerate caller-defined origins.
- **The handle is thread-safe**: calls on one `HawdbDatabase` are
  serialized internally. Callers that want per-thread parallelism open
  multiple handles.
- **Panic containment**: every entry point runs under `catch_unwind`;
  a panic reports `{"kind": "panic"}` instead of unwinding across FFI.

## Value encoding

Parameters and results are JSON so hosts never see HawDB's `Value` type.

- Cypher `hawdb_query`: `params_json` is a JSON object of `$name` values.
- SQL `hawdb_query_sql`: `params_json` is a JSON array of positional `$1`
  values.
- Results: `{"columns": [<name>, ...], "rows": [[<value>, ...], ...]}`.

| HawDB `Value` | JSON |
|---|---|
| Null | `null` |
| Bool | `true`/`false` |
| Int | integer |
| Float | number (`null` for non-finite) |
| Decimal | `{"$decimal": "<exact decimal text>"}` |
| String | string |
| Binary | `{"$binary": "<base64>"}` |
| Uuid | `{"$uuid": "<canonical text>"}` |
| Date, LocalTime, LocalDateTime, DateTime, Duration | `{"$date": ...}`, `{"$localtime": ...}`, `{"$localdatetime": ...}`, `{"$datetime": ...}`, `{"$duration": ...}` (ISO 8601 text) |
| List | array |
| Map | object |

`{"$binary": ...}`, `{"$uuid": ...}`, and `{"$decimal": ...}` decode back to
their native types in parameters; any other object shape stays a `Map`.
Decimal uses at most 38 coefficient digits and scale 0 through 38. Its JSON
payload must be a string; invalid or out-of-range values are rejected.
SQL `TIMESTAMP` columns read and bind as `$localdatetime` and `TIMESTAMPTZ`
columns as `$datetime`, returned in UTC (`...Z`); a `$datetime` parameter with
any offset is stored as its UTC instant.
The experimental retained ABI has no Decimal buffer type and reports
`HAWDB_RETAINED_UNSUPPORTED_TYPE` for Decimal node scalar access. Use ordinary
JSON queries for exact Decimal results.

## Transactions

Statements normally autocommit. To make several statements atomic, run them
inside the handle's transaction:

```c
hawdb_begin_transaction(db, &err);
hawdb_transaction_query_sql(db, insert_event, len, params, params_len, &res, &err);
hawdb_transaction_query_sql(db, update_projection, len, NULL, 0, &res, &err);
hawdb_transaction_query(db, cypher, len, NULL, 0, &res, &err); /* Cypher too */
hawdb_commit_transaction(db, &res, &err);   /* or hawdb_rollback_transaction(db, &err) */
```

- The transaction belongs to the database handle; there is no separate
  transaction pointer to free or to outlive its database. A handle has at
  most one open transaction; nesting fails with `kind: "transaction_open"`.
- Statements in the transaction see its own writes. Nothing outside the
  transaction sees them until `hawdb_commit_transaction` publishes all of them
  as one durable commit (under the handle's `durability` option).
- While a transaction is open, `hawdb_query` / `hawdb_query_sql` on that
  handle fail with `transaction_open`. Transaction calls, commit and rollback
  without an open transaction (including after a commit or rollback) fail
  with `kind: "no_transaction"`. SQL `BEGIN` / `COMMIT` stay rejected.
- A failed statement leaves the transaction open; roll it back. Commit
  closes the transaction whether or not it succeeds.
- A commit is all or nothing, never partial. A commit refused before it
  publishes (for example a write conflict or a budget refusal) leaves none of
  its statements. A successful return means all of them are durable (under
  the handle's `durability` option).
- `hawdb_close` on a handle with an open transaction rolls it back, and a
  process crash before `hawdb_commit_transaction` is called recovers none of
  the transaction's statements.
- A lost acknowledgment does not prove rollback. If the process dies while
  `hawdb_commit_transaction` is running, the commit may already be durable
  even though the caller never saw it return; an error raised while
  publishing is equally uncertain. Recovery then shows either the whole
  transaction or none of it. Reconcile against the reopened database, or make
  the retry idempotent, rather than blindly running the transaction again.
## Backup, restore and scrub

Each call returns a JSON report through `report_out` (unsigned 64-bit counts;
preserve their precision) or fills `err_out`:

- `hawdb_backup(db, dest_path, dest_len, &report, &err)` checkpoints the open
  database and writes a self-verifying backup directory to `dest_path`, which
  must not exist yet (its parent must). The backup holds every transaction
  committed before the call; the handle stays open. Report: `generation`,
  `checkpoint_commit_epoch`, `file_count`, `total_bytes`, `manifest_checksum`.
  Read-only and in-memory handles are refused.
- `hawdb_restore(src_path, src_len, dest_path, dest_len, &report, &err)`
  needs no handle. It verifies every backup file (length, CRC32C, SHA-256)
  before writing a new database directory at `dest_path`, then reports the
  same fields as the backup. A damaged backup or an existing destination fails
  without creating `dest_path`. Open the result with `hawdb_open`.
- `hawdb_scrub(db, &report, &err)` verifies the open database's published
  files and WAL against their checksums. Report: `generation`,
  `checked_file_count`, `checked_bytes`, `sha256_verified_file_count`,
  `wal_record_count`, `wal_bytes`. Damage fails with the engine's storage
  error and a message naming the mismatch, and poisons that handle: later
  statements fail until it is closed and the database reopened, or restored
  from a backup. Read-only handles can be scrubbed.

## Options

`hawdb_open` takes `options_json`, NULL or a JSON object. Each key is optional
and sets the typed Rust field of the same name; absent keys keep the embedded
defaults. Unknown keys and ill-typed values fail with `invalid_argument`
before the database path is touched.

| Key | Values | Default | Rust field |
|---|---|---|---|
| `read_only` | bool | `false` | `DatabaseConfig::read_only` (also selects strict recovery) |
| `durability` | `"sync_on_every_write"`, `"sync_on_checkpoint"` | `"sync_on_every_write"` | `HawDBEmbeddedOpenOptions::durability` |
| `max_read_result_rows` | integer >= 0, or `null` | `null` (no ceiling) | `DatabaseConfig::max_read_result_rows` |
| `max_read_result_payload_bytes` | integer > 0 | `67108864` (64 MiB) | `DatabaseConfig::max_read_result_payload_bytes` |
| `relational_monotonic_append_fast_path` | bool | `false` | `DatabaseConfig::relational_monotonic_append_fast_path` |

```json
{"durability": "sync_on_checkpoint", "relational_monotonic_append_fast_path": true,
 "max_read_result_rows": 10000, "max_read_result_payload_bytes": 8388608}
```

The default is power-loss safe: every commit is synchronized before it is
acknowledged. `"sync_on_checkpoint"` is an explicit host choice for write-heavy
workloads such as event logs: a commit's complete WAL is flushed to the OS
before it is acknowledged, but storage is synchronized only at checkpoint
boundaries, so a power failure (not a process crash) can lose recently
acknowledged transactions. Recovery never exposes part of a transaction, and
branch creation, deletion and head publication remain power-loss safe.
Options apply to one open; reopening without them restores the defaults.

`max_read_result_rows` of `0` or `null` disables the host row ceiling. The
payload budget can be lowered or raised but not removed. A read over either
budget fails (`read_budget_exceeded`, or `resource_budget_exceeded` with a
`resource_budget` object) instead of returning a partial result.

`relational_monotonic_append_fast_path` enables the metadata-only INSERT path
for RowPage tables whose primary keys arrive in increasing order. Inserts that
are out of order or duplicate fall back to the ordinary checked path with the
same results and errors.

One handle serializes its calls, so it has no group-commit setting; Rust hosts
that need WAL group commit across concurrent writers use `ConcurrentDatabase`.

## Experimental retained numeric ABI

The additive `hawdb_retained_*` exports use ABI version 1, checked descriptor
sizes, fixed-width discriminants and opaque namespace/ID handles. This is an
experimental adapter for the root numeric cursor described in
[the retained delivery notes](../../docs/RETAINED_NUMERIC_CORE.md).
Source capacity and native construction are admitted by the landed numeric core.
Complete foreign allocation/RSS and performance qualification remain open;
Arrow export is a separate delivery. An experimental purego numeric
adapter is described in [the Go notes](../go/README.md); its complete resource
and platform qualification remains open. This does not qualify general queries,
source reuse or a whole-operation memory bound.

`hawdb_retained_query` takes UTF-8 Cypher and ordinary parameter JSON through
`HawdbRetainedQueryV1`. It fixes the schema before pulling and refuses other
plans, source-reuse and writable requests explicitly. Root support is one-label
integer/float filtering with projections of the same property or unsigned
`id(n)`, optionally SKIP/LIMIT. The public property type must already be declared.
Results use native read-only buffers, with no JSON result serialization.

Check the returned status code on every call. `hawdb_retained_next` returns
`HAWDB_RETAINED_OK`, `HAWDB_RETAINED_EOF`, recoverable
`HAWDB_RETAINED_BACKPRESSURE`, or a distinct failure. Outputs are emptied before
fallible work; EOF never carries a batch owner. Release held views and retry
backpressure on the same cursor. Terminal failures repeat rather than become
EOF. Default pulls remain serial with two distinct payload slots and no prefetch.

Each batch describes physical rows and ordered u32 selection indices. Numeric
column data has one element per physical row; use selection indices to obtain
the result rows. Repeated property projections share their value allocation.
Buffer provenance includes namespace/allocation/generation, retained capacity
and visible byte range. The data pointer already addresses that visible range;
do not add byte_offset a second time.

`hawdb_retained_column_borrow` exposes an immutable range tied to an existing
batch, without another allocation or handle. Its BORROWED flag means it must not
be released independently. `hawdb_retained_column`, column retain and batch
retain create separately admitted owners. Their pointers survive parent batch,
cursor and database closure until their own final release. All-valid columns
have no validity buffer; other columns expose native u64 bitmap words with
least-significant-bit row order. Schemas distinguish nullable Int64/Float64
properties from non-null UInt64 node identities.

Call `hawdb_retained_state` to observe late status changes; earlier batches are
provisional until Completed. Cursor close stops pulls and releases the source
without revoking produced data. Release each independent owner exactly once
with `hawdb_retained_release`. Unknown, wrong-module and released handles refuse
without dereferencing them. Namespace/ID values are lifetime identifiers, not an
authorization boundary. Borrowed pointer reads require a live owner; do not race
those reads with release. Keep the library mapped until all owners are released.

Adapter object/descriptor capacities are prepaid by the root cursor before
allocation or source advancement. A pull also prepays the borrowed column
descriptor set, so reading a held batch needs no extra admission. Metadata is
charged through the original shared runtime and query ledger; keeping more
cursors or views cannot create a new allowance. C creation requires at least
three shared handles for control, first batch and one independent column. A
smaller configuration refuses before binding, allowing correction. No default
result byte limit, durability mode or persistent format changes.

Independent batch retains also prepay the borrowed column descriptor set;
admission may refuse before constructing a new owner. Closed cursor pulls
return Closed without manufacturing a terminal failure. A caught panic after
source advancement, including descriptor registration, fails the cursor
terminally; retry cannot silently skip the undelivered batch.

The root Rust Arrow interface is separate from this native retained C ABI.
Its array/stream data exports currently require little-endian validity words.
Empty/contiguous selections share payload; an Arrow stream can deliver earlier
arrays and then fail with errno 22 on a later sparse selection. Those arrays
remain readable but are an incomplete result. No pre-scan or gather occurs.
Errno 12 covers retryable pressure and terminal capacity/budget errors; use the
diagnostic or the native typed retained statuses to classify the failure.
